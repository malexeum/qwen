# Технический план правок перед переходом к benchmark-runner

## Назначение документа

Документ фиксирует список обязательных правок перед переходом от протокольного шага к полному `benchmark-runner` для фрактального движка. Текущий этап уже правильно построен как воспроизводимый исследовательский каркас с `frozen_run_config.json`, режимами вычислений и шаблоном метрик, поэтому следующий шаг должен не ломать эту дисциплину, а превратить её в серийный и статистически корректный экспериментальный конвейер [cite:138].

Главная цель правок — убрать методологические смешения, повысить сопоставимость результатов между генераторами и сделать так, чтобы итоговые таблицы действительно отвечали на исследовательский вопрос: какой класс нелинейных преобразований лучше сохраняет идентичность входной гармонической структуры при переводе в новое фрактальное состояние [cite:138].

## 1. Зафиксировать границы второго этапа

Перед запуском `benchmark-runner` необходимо явно сузить задачу второго этапа. На этом шаге исследуется не полный pipeline и не коммерческий продукт, а сравнительная способность классов генераторов сохранять внутриклассовую связность и обеспечивать межклассовую различимость в пространстве наблюдаемых признаков [cite:138].

### Обязательные ограничения этапа 2

- Исключить любые новые обучаемые компоненты из benchmark-цикла.
- Если энкодер уже существует, использовать только полностью замороженную версию с фиксированными весами и фиксированной версией признакового пространства.
- Не смешивать проверку генератора и проверку энкодера в одном сравнении.
- Не добавлять UI, веб-обвязку и вторичную стилизацию.
- Считать benchmark-runner исследовательским модулем, а не демонстрационным инструментом.

### Формулировка цели этапа 2

`benchmark-runner` должен проверять, какой набор генераторов и правил отображения максимизирует:

- низкую `within-class` дистанцию;
- высокую `between-class` дистанцию;
- устойчивость к малым возмущениям;
- управляемую вариативность внутри семейства;
- интерпретируемость результата по генератору, seed и классу входа.

## 2. Убрать методологическое смешение генератора и энкодера

В текущем описании введён обучаемый оператор вида \\( \theta = E_\phi(H) \\), но на следующем шаге это создаёт риск смешать качество отображения входа в параметры с качеством самого нелинейного генератора [cite:138]. До отдельного этапа обучения необходимо сравнивать генераторы на одинаковом, явном и фиксированном mapping-слое.

### Правка

Для benchmark-этапа ввести только два допустимых режима задания параметров генератора:

- `rule_based_mapping` — детерминированное отображение из входного класса в параметры генератора;
- `frozen_encoder_mapping` — разрешается только при наличии полностью фиксированной версии модели и отдельной записи её версии в конфиге.

### Обязательные поля в конфиге

Добавить в `frozen_run_config.json`:

```json
{
  "mapping_mode": "rule_based_mapping",
  "mapping_version": "v1.0",
  "encoder_enabled": false,
  "encoder_version": null,
  "feature_schema_version": "v1.0",
  "observer_version": "v1.0",
  "distance_metric_version": "v1.0"
}
```

## 3. Явно определить набор входных классов

Сейчас в протоколе есть эксперименты и генераторы, но не до конца формализован реестр классов входа, а без этого `within-class` и `between-class` дистанции рискуют остаться красивыми, но плохо интерпретируемыми числами [cite:138]. Перед следующим шагом нужен компактный и фиксированный набор классов.

### Требование

Создать `input_registry.json` или `input_registry.yaml`, где для каждого входного класса заданы:

- имя класса;
- краткое описание структуры;
- базовый вектор признаков;
- допустимые диапазоны внутриклассовых деформаций;
- число инстансов на класс;
- число контролируемых возмущений;
- класс-родитель, если используется иерархия.

### Рекомендуемый минимальный состав

- 4–6 классов;
- по 5–10 инстансов на класс;
- для каждого инстанса — 3 уровня малых возмущений;
- отдельный набор для `family_deformation`;
- отдельный набор для `separability`.

### Пример структуры

```yaml
classes:
  - name: harmonic_symmetric
    base_vector: [0.8, 0.2, 0.7, 0.3, 0.9, 0.4]
    perturbation_scales: [0.01, 0.03, 0.05]
    n_instances: 8
  - name: harmonic_dense_irregular
    base_vector: [0.4, 0.9, 0.3, 0.8, 0.2, 0.7]
    perturbation_scales: [0.01, 0.03, 0.05]
    n_instances: 8
```

## 4. Разделить типы шума и вариативности

В текущем протоколе уже есть `stochastic_scale`, но для следующего шага необходимо развести разные источники неопределённости, иначе невозможно понять, откуда пришла нестабильность — из seed, из параметрической деформации или из оператора наблюдения [cite:138].

### Правка

Разделить шум на три независимых компонента:

- `seed_noise` — случайность генератора при фиксированном классе и фиксированных параметрах;
- `parameter_noise` — малое возмущение управляющих параметров генератора;
- `observer_noise` — вариативность, вносимая постобработкой, дискретизацией или способом наблюдения.

### Пример поля конфигурации

```yaml
noise:
  seed_noise:
    julia_orbit_trap: 0.01
    orbit_ifs_multi_trap: 0.0
    duffing_lyapunov: 0.002
    chaotic_scattering: 0.0005
  parameter_noise:
    default_scale: 0.01
  observer_noise:
    enabled: false
    scale: 0.0
```

## 5. Нормировать пространство признаков перед расчётом дистанций

В отчёте фиксируются морфологические признаки и итоговые дистанции между выходами, но без явной нормировки разные шкалы признаков могут доминировать в `within_mean` и `between_mean` просто из-за масштаба [cite:138]. Это особенно опасно при смешении basin-метрик, симметрии и proxy фрактальной размерности в одном векторе.

### Правка

Перед расчётом любых дистанций runner обязан:

- собрать полный вектор признаков `z`;
- применить фиксированный способ масштабирования;
- сохранять и сырые, и нормированные значения;
- записывать в отчёт используемую схему нормировки.

### Допустимые варианты нормировки

- `zscore_per_feature`;
- `robust_zscore_per_feature`;
- `minmax_per_feature` — только для отладочного режима;
- `whitened_embedding` — только если используется и зафиксирован заранее.

### Обязательные поля

```json
{
  "feature_normalization": "robust_zscore_per_feature",
  "store_raw_features": true,
  "store_normalized_features": true
}
```

## 6. Добавить baseline-модели

Сравнение только между сложными генераторами не даёт ответа, являются ли полученные результаты действительно сильными или просто внутренне согласованными [cite:138]. Перед следующим шагом обязательно добавить простые baseline-варианты.

### Обязательные baseline-классы

- `random_baseline` — случайное распределение параметров в допустимом диапазоне;
- `smooth_geometric_baseline` — простой детерминированный генератор без выраженной фрактальной динамики;
- `single_parameter_map_baseline` — отображение, зависящее от одного-двух параметров без сложной нелинейной структуры.

### Цель baseline

- показать, что сложные нелинейные режимы действительно выигрывают;
- отделить фрактальную идентичность от просто красивой геометрии;
- проверить, не слишком ли легко separability возникает сама по себе.

## 7. Сделать benchmark-runner полностью факторным

На следующем шаге runner не должен запускать “сценарии вручную”. Он должен проходить полное пространство комбинаций параметров, определённое frozen-конфигом и реестром входов [cite:138].

### Минимальное пространство перебора

Runner должен итерировать по декартову произведению:

- `generator`;
- `experiment`;
- `class_name`;
- `instance_id`;
- `seed`;
- `noise_level`;
- `deformation_step`;
- `mapping_mode`.

### Требование к исполнению

- Каждая комбинация должна иметь уникальный `run_id`.
- Любой упавший прогон должен быть перезапускаем без пересчёта всего набора.
- Runner должен поддерживать `resume` и `skip_completed=true`.
- Для каждого run должна писаться отдельная строка в `run_table.csv`.

## 8. Расширить набор обязательных артефактов

Сейчас подготовлены `frozen_run_config.json`, копия YAML и шаблон CSV, чего достаточно для протокольного шага, но недостаточно для серийной исследовательской кухни [cite:138]. Следующий этап должен производить полный набор сырых, агрегированных и интерпретационных артефактов.

### Обязательные файлы benchmark-runner

- `run_table.csv` — одна строка на один элементарный прогон;
- `features_raw.parquet` или `features_raw.csv` — сырые векторы признаков;
- `features_normalized.parquet` или `features_normalized.csv` — нормированные признаки;
- `aggregate_by_class.csv`;
- `aggregate_by_generator.csv`;
- `aggregate_by_experiment.csv`;
- `pairwise_distance_matrix.csv`;
- `retrieval_accuracy.csv`;
- `bifurcation_events.csv`;
- `summary.json`;
- `research_report.md`.

### Дополнительные полезные артефакты

- `failed_runs.csv`;
- `timing_profile.csv`;
- `manifest_full.json`;
- `top_examples/` с лучшими и худшими случаями.

## 9. Уточнить статистическую агрегацию

Средние значения недостаточны, потому что нелинейные генераторы могут иметь тяжёлые хвосты распределений и редкие, но важные переходные режимы [cite:138]. Runner должен по умолчанию считать не только mean, но и устойчивые статистики разброса.

### Для каждой метрики считать

- `mean`;
- `std`;
- `median`;
- `iqr`;
- `min`;
- `max`;
- `n`;
- bootstrap confidence interval 95%.

### Для таблиц ранжирования использовать

- основную сортировку по median;
- дополнительную сортировку по lower CI bound;
- отдельный флаг нестабильности, если `cv` или IQR превышают порог.

## 10. Усилить набор метрик

Текущий список метрик уже полезен, но его недостаточно для полной интерпретации связки “устойчивость + различимость + управляемая вариативность” [cite:138].

### Оставить как обязательные

- `mean_cv`;
- `max_cv`;
- `within_mean`;
- `between_mean`;
- `separability`;
- `cohesion_ratio`;
- `basin_entropy`;
- `symmetry_score`;
- `fractal_dim_proxy`;
- `n_bifurcations`.

### Добавить

- `seed_sensitivity`;
- `input_perturbation_sensitivity`;
- `observer_variance`;
- `silhouette_like_score`;
- `top1_class_retrieval`;
- `top3_class_retrieval`;
- `stability_diversity_ratio`;
- `family_continuity_score`.

### Интерпретация

- Высокий `within_mean` — плохо.
- Высокий `between_mean` — хорошо.
- Высокий `separability` — хорошо, но только вместе с контролем разброса.
- Слишком низкий `seed_sensitivity` может означать вырожденный генератор.
- Слишком высокий `seed_sensitivity` может означать потерю идентичности.

## 11. Усилить детектор бифуркаций

Текущий z-score по дискретному градиенту годится как автоматический инженерный детектор, но он чувствителен к масштабу признаков и шуму [cite:138]. Перед следующим шагом критерий стоит сделать двухступенчатым.

### Правка

Использовать двухуровневую схему:

1. Локальное сглаживание последовательности \\( z_i \\) по окну.
2. Расчёт дискретного градиента.
3. Z-score проверка.
4. Подтверждение события, только если скачок устойчив на локальном интервале длиной не менее `k` точек.

### Обязательные параметры

```yaml
bifurcation_detection:
  smoothing_window: 3
  z_threshold: 2.5
  persistence_points: 2
  min_jump_norm: 0.15
```

### Выходные поля в `bifurcation_events.csv`

- `generator`;
- `class_name`;
- `parameter_name`;
- `parameter_value`;
- `gradient_norm`;
- `zscore`;
- `confirmed_event`.

## 12. Разделить общие и generator-specific признаки

Один и тот же вектор признаков не обязан одинаково хорошо описывать Julia orbit traps, IFS, Duffing-карты и chaotic scattering, а сейчас есть риск переоценить удобные для одних генераторов признаки и недооценить другие [cite:138].

### Правка

Ввести два уровня признаков:

- `common_features` — единые для всех генераторов;
- `generator_specific_features` — включаются только для определённых семейств.

### Пример

Общие:
- `symmetry_score`;
- `fractal_dim_proxy`;
- `basin_entropy`;
- `density_variation`.

Специфические:
- для `duffing_lyapunov`: Lyapunov-like stability descriptors;
- для `chaotic_scattering`: escape-time distribution statistics;
- для `orbit_ifs_multi_trap`: orbit occupancy and trap interaction scores.

## 13. Добавить hi-res валидацию лучших режимов

Текущий режим `publication` с разрешением 192x192 может быть недостаточен для надёжного анализа тонких морфологических различий, особенно у basin-структур и scattering-паттернов [cite:138]. Для таблиц и массовых прогонов этого может хватать, но лучшие режимы нужно отдельно перепроверять.

### Правка

Добавить служебный режим:

```yaml
validation-hires:
  resolution_default: [384, 384]
  resolution_duffing: [384, 384]
  resolution_scattering: [384, 384]
  repeats_per_class: 5
  sensitivity_steps: 31
  deformation_steps: 12
  duffing_steps: 600
  ifs_points: 100000
```

### Назначение

- повторная проверка топ-3 генераторов;
- проверка устойчивости метрик к увеличению разрешения;
- исключение артефактов грубой сетки.

## 14. Обязательное сохранение сырых наблюдений и признаков

Следующий этап должен позволять пересчитывать новые метрики без полного rerun, иначе любое изменение аналитики будет слишком дорогим [cite:138]. Это особенно важно для исследовательской разработки, где полезные идеи почти всегда появляются после первого полного прогона.

### Правка

Для каждого run сохранять:

- ссылку на изображение или поле наблюдения;
- сырое состояние признаков `z_raw`;
- нормированное состояние `z_norm`;
- версию наблюдателя;
- версию извлекателя признаков.

### Формат

Предпочтительно `parquet` для признаков и `png`/`npy` для наблюдений.

## 15. Стандартизовать структуру финального отчёта

Markdown-отчёт следующего шага не должен быть просто дампом таблиц. Он должен отвечать на исследовательский вопрос и одинаково читаться как внутренний research memo и как заготовка для статьи [cite:138].

### Обязательная структура `research_report.md`

1. Цель benchmark-этапа.
2. Frozen-конфиг и версии всех компонентов.
3. Набор генераторов.
4. Набор входных классов.
5. Использованные признаки и нормировка.
6. Таблица основных метрик по генераторам.
7. Within-class / between-class результаты.
8. Анализ чувствительности и деформаций.
9. Бифуркационные события.
10. Лучшие и худшие режимы.
11. Вывод: какой генератор или класс генераторов рекомендован для следующего этапа.

### Отдельный блок выводов

В финале отчёта должны быть короткие ответы на три вопроса:

- какой генератор лучше всего удерживает идентичность класса;
- какой генератор даёт лучшую различимость;
- какой генератор лучше всего балансирует устойчивость и новизну.

## 16. Ввести критерии готовности к переходу на следующий этап

После benchmark-runner должен быть момент принятия решения, а не бесконечная генерация новых таблиц. Поэтому до запуска надо зафиксировать критерии, по которым генератор или семейство режимов проходит дальше.

### Минимальные критерии перехода

- `separability` статистически выше baseline;
- `within_mean` стабильно ниже порога;
- `family_continuity_score` выше минимального значения;
- результаты устойчивы на `validation-hires`;
- нет критической зависимости выводов от одного seed или одного класса.

### Формат решения

В конце `summary.json` должен быть блок:

```json
{
  "stage2_decision": {
    "recommended_generators": ["julia_orbit_trap", "duffing_lyapunov"],
    "rejected_generators": ["random_baseline"],
    "decision_reason": "best balance of separability, cohesion and robustness"
  }
}
```

## Приоритет внедрения правок

### Критично до запуска runner

- зафиксировать входные классы;
- убрать смешение энкодера и генератора;
- ввести нормировку признаков;
- добавить baseline;
- реализовать факторный run-table;
- настроить сохранение сырых признаков;
- расширить статистическую агрегацию.

### Желательно в первую итерацию runner

- улучшить бифуркационный детектор;
- разделить common и generator-specific признаки;
- добавить retrieval-метрики;
- стандартизовать финальный markdown-отчёт.

### Можно сделать после первого полного прогона

- `validation-hires`;
- дополнительные генератор-специфические метрики;
- автоматический выбор лучшего семейства режимов;
- полуавтоматическую генерацию таблиц для статьи.

## Итоговая рекомендация

Переход к `benchmark-runner` действительно своевременен, но только при условии, что второй этап будет поставлен как строгий факторный эксперимент, а не как массовый запуск уже существующего шаблона [cite:138]. Главный смысл всех правок — сделать так, чтобы benchmark отвечал не на вопрос «что получилось красивее», а на вопрос «какой класс нелинейных преобразований лучше всего сохраняет идентичность гармонической структуры при переводе в новое фрактальное состояние» [cite:138].
