# Задача архитектору проекта: MVP приложения для генерации визуалов по треку

## Контекст

У нас уже есть сильная исследовательская база: серия benchmark-экспериментов v4.x показала, что система умеет различать классы, генераторы, семейства и режимы распада идентичности. Это полезно не как конечный продукт, а как **фундамент** для продуктовой архитектуры: из наблюдательной и исследовательской системы нужно собрать понятный MVP для пользователя.

Главная продуктовая идея MVP:

- пользователь загружает трек;
- система анализирует аудио;
- генерируется 1 статичный постер;
- генерируется 1 короткий loop-видео;
- пользователь выбирает стиль: `техно`, `классика`, `эмбиент`, `кинематографично`;
- результат можно экспортировать в high-res и в форматы для соцсетей.

## Что уже есть

### 1. Исследовательская база и метрики

У нас уже есть рабочая benchmark-логика, которая измеряет:

- preservation / transformation / breakage;
- family continuity;
- class stability;
- morphology persistence;
- observer stability;
- bifurcation events;
- separability;
- retrieval accuracy.

Это означает, что у нас уже есть не просто генератор, а **семантическая карта поведения систем**. Для MVP это можно переиспользовать как основу для style ontology и выбора визуальных режимов.

### 2. Генераторная и стилeвая ось

Из экспериментов уже видно, что разные семейства ведут себя по-разному:

- `duffing_lyapunov` — сильный носитель continuity и identity;
- `single_parameter_map_baseline` — селективно сильный baseline;
- `smooth_geometric_baseline` — морфологически гладкий, но часто чужой по identity;
- `random_baseline` — отрицательный контроль.

Для продукта это означает: можно строить **style families**, а не набор случайных шаблонов.

### 3. Архитектурное понимание MVP

Уже понятно, что MVP не должен пытаться решать все задачи сразу. Нужен один ясный пользовательский сценарий:

- upload track → audio analysis → style selection → poster/loop generation → export.

Это правильная точка входа для продукта.

## Цель архитектора

Архитектор должен спроектировать **минимальную, но расширяемую продуктовую архитектуру**, которая:

1. поддерживает один основной сценарий;
2. отделяет анализ аудио от генерации визуала;
3. позволяет добавлять стили без переписывания ядра;
4. готова к будущему расширению в полноценный творческий инструмент;
5. сохраняет связь с исследовательской частью проекта.

## Основной пользовательский сценарий

1. Пользователь загружает аудиотрек.
2. Система извлекает аудио-признаки.
3. Система выбирает подходящий style profile.
4. Пользователь при необходимости выбирает стиль вручную.
5. Генерируется постер.
6. Генерируется loop-видео.
7. Пользователь просматривает результат.
8. Пользователь экспортирует результат в high-res или соцсети.

## Что должен спроектировать архитектор

### 1. Доменную модель

Нужно определить основные сущности:

- `Track`
- `AudioAnalysis`
- `StyleProfile`
- `GenerationJob`
- `PosterAsset`
- `LoopVideoAsset`
- `ExportJob`
- `UserProject`

Для каждой сущности нужно определить:

- поля;
- связи;
- жизненный цикл;
- где хранится состояние;
- какие данные считаются derived, а какие authoritative.

### 2. Пайплайн обработки

Нужен четкий pipeline:

`Upload → Validate → Analyze → Select Style → Generate Poster → Generate Loop → Preview → Export`

Архитектор должен разделить:

- входные данные;
- анализ;
- генерацию;
- рендер;
- экспорт.

Это критично, чтобы потом можно было менять стили, модели и форматы вывода без поломки всей системы.

### 3. Систему стилей

Нужно спроектировать style engine, в котором стиль — это не просто название, а набор параметров:

- палитра;
- контраст;
- геометрия;
- плотность;
- motion intensity;
- temporal rhythm;
- noise level;
- symmetry bias;
- structure complexity.

Минимальный набор стилей для MVP:

- `techno`
- `classical`
- `ambient`
- `cinematic`

Каждый стиль должен иметь profile-конфиг и возможность подстройки под анализ трека.

### 4. Систему генерации

Нужно определить, как будет строиться генерация:

- от аудио-признаков к визуальным параметрам;
- от style profile к posterior render parameters;
- от генерации постера к генерации loop-видео.

Важно, чтобы один и тот же анализ мог давать несколько визуальных интерпретаций в зависимости от стиля.

### 5. Экспортный слой

Нужно заранее заложить:

- PNG / JPG для постера;
- MP4 / WebM для loop;
- presets для соцсетей;
- high-res render path.

Экспорт должен быть отдельным слоем, а не частью генератора.

## Архитектурные принципы

### Обязательно

- Разделить analysis и generation.
- Делать style profiles конфигурируемыми.
- Хранить результат как project entity, а не только как временный render.
- Поддержать повторную генерацию без повторной загрузки трека.
- Сделать систему расширяемой под новые стили и новые форматы.

### Нельзя

- Не связывать UI напрямую с генераторным ядром.
- Не хардкодить стили в одном месте.
- Не смешивать исследовательские метрики benchmark-а с продуктовой логикой.
- Не делать сложный editor на первом этапе.
- Не строить архитектуру вокруг абстрактного “всё можно”, вместо одного сценария.

## Связь с исследовательской базой

Исследовательские результаты benchmark v4.x должны быть использованы как источник идей для style ontology:

- генераторные семейства можно переосмыслить как визуальные семейства;
- continuity можно использовать как аналог устойчивости стиля;
- broken / transformed состояния можно использовать как режимы вариации;
- morphology persistence можно использовать как визуальную согласованность;
- observer stability — как устойчивость интерпретации при повторном рендере.

Но важно: **продуктовая архитектура не должна зависеть от research code напрямую**. Нужен слой адаптации.

## Рекомендуемая архитектурная схема

### Frontend

- upload screen;
- style selection screen;
- preview screen;
- export screen;
- project history.

### Backend

- audio ingestion service;
- audio analysis service;
- style resolution service;
- poster generation service;
- loop generation service;
- export service;
- project storage service.

### Storage

- raw audio;
- analysis JSON;
- style profile JSON/YAML;
- poster assets;
- loop assets;

## Минимальный набор API

- `POST /upload`
- `POST /analyze`
- `POST /generate/poster`
- `POST /generate/loop`
- `POST /export`
- `GET /project/{id}`
- `GET /project/{id}/preview`

## Результат, который должен выдать архитектор

Архитектор должен подготовить документ, в котором будут:

1. доменная модель;
2. схема пайплайна;
3. схема сервисов;
4. описание style engine;
5. описание экспортного слоя;
6. список MVP-scope и out-of-scope;
7. рекомендации по следующему этапу разработки.

## Критерии успеха

Архитектура считается готовой, если:

- она поддерживает один четкий сценарий;
- она не зависит от случайных исследовательских деталей;
- в ней можно легко добавить новые стили;
- она позволяет генерировать и постер, и loop;
- она готова к дальнейшему расширению без переделки ядра.

## Формулировка задачи в одной строке

**Спроектировать MVP-архитектуру приложения для анализа аудио и генерации постера + loop-видео с выбором стиля, опираясь на research-слой только как на источник style ontology, но не смешивая его с продуктовой логикой.**

## Примечание

Двигаемся осторожно и последовательно: сначала ясный MVP, потом расширение. С Божьей помощью, но с хорошей архитектурой.
