# Техническое задание: sanity-check v3 и калибровка generator-specific thresholds

## 1. Цель

Необходимо доработать скрипт визуальной проверки и слой identity-классификации так, чтобы система могла:

- калибровать пороги отдельно для каждого генератора;
- не путать хрупкую трансформацию с поломкой структуры;
- корректно различать `preserved`, `transformed`, `weakly-transformed`, `broken`, `emergent`;
- сохранять короткий sanity-check режим для быстрой проверки визуала;
- формировать воспроизводимый threshold profile для каждого генератора.

Цель v3 — перейти от общих глобальных порогов к **generator-specific thresholds**, потому что текущие наблюдения показали, что разные генераторы имеют принципиально разные зоны устойчивости.

## 2. Контекст и проблема

По результатам предыдущих прогонов стало ясно, что:

- `julia_orbit_trap` очень хрупкая и ломается уже при относительно небольшом увеличении `score`;
- `orbit_ifs_multi_trap` долго сохраняет форму и меняет в основном плотность/яркость;
- `duffing_lyapunov` имеет чёткую границу перехода между мягкой трансформацией и разрушением;
- единые глобальные пороги для всех генераторов искажают интерпретацию.

Следовательно, нужен отдельный режим, который:

1. прогоняет небольшой набор контрольных комбинаций;
2. измеряет поведение по шагам деформации;
3. подбирает threshold profile для каждого генератора;
4. сохраняет калиброванный результат в конфиг и отчёт.

## 3. Область работ

### Входит в scope

- добавление режима `sanity_check_v3`;
- калибровка threshold profiles по генераторам;
- сохранение результатов в отдельную папку;
- генерация manifest и summary;
- обновление identity layer для работы с generator-specific thresholds;
- добавление профилей порогов в конфиг или taxonomy-файл.

### Не входит в scope

- полный benchmark-runner;
- обучение новых моделей;
- изменение визуального стиля;
- новый UI;
- расширенный многоклассовый benchmark.

## 4. Генераторы и режимы

### 4.1 Генераторы для sanity-check v3

Использовать только:

- `julia_orbit_trap`
- `orbit_ifs_multi_trap`
- `duffing_lyapunov`

### 4.2 Input class

Использовать только:

- `harmonic_symmetric`

### 4.3 Seeds

Использовать фиксированный набор seed:

- `42`
- `101`
- `999`

### 4.4 Deformation steps

Минимальный набор для калибровки:

- `1`
- `3`
- `5`
- `7`
- `9`
- `12`
- `15`
- `16`
- `20`

Если для конкретного генератора нужно меньше или больше точек, это задаётся в generator-specific profile.

## 5. Требования к режиму sanity-check v3

### 5.1 Отдельный режим запуска

Скрипт должен поддерживать новый режим:

```json
{
  "mode": "sanity_check_v3"
}
```

### 5.2 Изоляция вывода

Все результаты должны сохраняться отдельно от основного benchmark:

- папка `sanity_check_v3_outputs/`;
- отдельный manifest;
- отдельный summary;
- отдельная папка изображений.

### 5.3 Визуальная цель

Режим предназначен не для массового анализа, а для быстрой, управляемой проверки:

- где начинается `transformed`;
- где структура становится `broken`;
- где генератор остаётся `weakly-transformed` слишком долго;
- насколько адекватны пороги по каждому семейству.

## 6. Generator-specific thresholds

### 6.1 Общее требование

Нужно убрать универсальные глобальные пороги и заменить их на пороги по каждому генератору.

### 6.2 Структура threshold profile

Для каждого генератора нужно сохранить:

- `preserved_threshold`
- `transformed_threshold`
- `broken_threshold`
- `weakly_transformed_threshold`
- `score_scale`
- `calibration_notes`
- `profile_version`

### 6.3 Пример структуры

```yaml
threshold_profiles:
  julia_orbit_trap:
    profile_version: v1.0
    preserved_threshold: 0.15
    transformed_threshold: 0.35
    broken_threshold: 0.45
    weakly_transformed_threshold: 0.28
    score_scale: 1.0
    calibration_notes: "Хрупкая зона; короткое окно трансформации"

  orbit_ifs_multi_trap:
    profile_version: v1.0
    preserved_threshold: 0.25
    transformed_threshold: 0.70
    broken_threshold: 0.95
    weakly_transformed_threshold: 0.55
    score_scale: 1.0
    calibration_notes: "Долгая зона сохранения формы; растёт плотность"

  duffing_lyapunov:
    profile_version: v1.0
    preserved_threshold: 0.12
    transformed_threshold: 0.30
    broken_threshold: 0.55
    weakly_transformed_threshold: 0.22
    score_scale: 1.0
    calibration_notes: "Переход в хаос между 9 и 12 шагом"
```

### 6.4 Важно

Числа выше — это не финальная истина, а пример структуры. Реальные значения должны быть получены из калибровочного прогона.

## 7. Логика классификации

### 7.1 Общий принцип

Identity layer должен присваивать label не по глобальному порогу, а по профилю конкретного генератора.

### 7.2 Требуемые labels

- `baseline`
- `preserved`
- `transformed-like`
- `weakly-transformed`
- `broken-like`
- `emergent-like`

### 7.3 Правило приоритета

Если score попадает сразу в несколько зон, применяется приоритет:

1. `broken-like`
2. `emergent-like`
3. `weakly-transformed`
4. `transformed-like`
5. `preserved`
6. `baseline`

### 7.4 Generator-specific decision rule

Классификация должна происходить по формуле вида:

```text
label = classify(score, generator_profile)
```

где `generator_profile` берётся из конфигурации по имени генератора.

## 8. Пошаговый план калибровки

### Шаг 1. Запуск sanity_check_v3

Скрипт прогоняет фиксированный набор:

- 1 input class;
- 3 generators;
- 3 seeds;
- набор deformation steps.

### Шаг 2. Сбор scores

Для каждой комбинации нужно сохранить:

- generator;
- seed;
- deformation_step;
- raw score;
- normalized score;
- preview label.

### Шаг 3. Анализ по генераторам

Нужно автоматически определить:

- где начинается `transformed-like`;
- где появляется `weakly-transformed`;
- где начинается `broken-like`.

### Шаг 4. Сохранение threshold profile

По результатам прогона необходимо сохранить отдельные пороги для каждого генератора.

### Шаг 5. Проверка верификации

После калибровки скрипт должен уметь повторно прогнать тот же sanity-check и показать, что labels стали стабильнее и ближе к визуальной интерпретации.

## 9. Output-файлы

### 9.1 `sanity_check_manifest.csv`

Одна строка на каждый run.

Минимальные поля:

- `run_id`
- `generator`
- `input_class`
- `seed`
- `deformation_step`
- `raw_score`
- `normalized_score`
- `preview_label`
- `status`
- `threshold_profile_version`
- `observer_version`
- `feature_schema_version`

### 9.2 `sanity_check_summary.json`

Должен содержать:

- количество прогонов;
- список генераторов;
- список шагов;
- распределение labels;
- калиброванные пороги по каждому генератору;
- замечания по поведению каждого генератора;
- список случаев, где label расходится с ожиданием.

### 9.3 `threshold_profiles.yaml`

Сохранённый итоговый профиль порогов.

### 9.4 Папка изображений

Каждый run должен сохранять изображение в отдельный файл с понятным именем.

## 10. Требования к логированию

### 10.1 Обязательные логи

Скрипт должен печатать в консоль:

- имя режима;
- input class;
- генератор;
- seed;
- deformation step;
- preview label;
- путь к результату;
- status.

### 10.2 Уровень детализации

Нужно вывести лог так, чтобы программист мог по тексту понять:

- где генератор ломается раньше;
- где происходит мягкая трансформация;
- где окно слишком узкое или слишком широкое.

## 11. Проверки правильности

### 11.1 Для `julia_orbit_trap`

Ожидается:

- очень короткое окно `transformed-like`;
- ранний переход в `broken-like`;
- высокая чувствительность к шагу деформации.

### 11.2 Для `orbit_ifs_multi_trap`

Ожидается:

- стабильное сохранение формы;
- долгий диапазон `weakly-transformed`;
- медленный рост score;
- поздний либо очень мягкий переход в broken.

### 11.3 Для `duffing_lyapunov`

Ожидается:

- плавная деформация до порога;
- чёткий переход между `transformed-like` и `broken-like`;
- ярко выраженная точка бифуркации.

## 12. Acceptance criteria

Задача считается выполненной, если:

1. Скрипт поддерживает режим `sanity_check_v3`.
2. Для каждого генератора используется собственный threshold profile.
3. Профили сохраняются в отдельный файл.
4. Manifest и summary формируются автоматически.
5. Классификация label-ов лучше соответствует визуальному поведению.
6. Можно повторно запустить тот же режим и получить сопоставимые результаты.
7. В отчёте видно, где генератор хрупкий, а где устойчивый.

## 13. Приоритеты реализации

### Сначала

- добавить `sanity_check_v3`;
- добавить generator-specific threshold profiles;
- добавить сохранение профилей;
- обновить manifest и summary.

### Затем

- улучшить label assignment;
- добавить score normalization;
- добавить better logging;
- добавить повторную калибровку по результатам прогона.

### После первой итерации

- связать профили с identity layer;
- подключить профили к benchmark v4;
- использовать профили в дальнейшем полном прогоне.

## 14. Итог

Benchmark v3 sanity-check должен стать компактным, но строгим способом калибровки порогов по каждому генератору. Главная идея — перестать трактовать все нелинейные системы одинаково и вместо этого учитывать, что у каждого генератора есть собственная зона устойчивости, собственная чувствительность и собственная точка разрушения.
